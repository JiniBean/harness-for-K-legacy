# set-up-harness

프로젝트 하나에 하네스를 깐다. 기능(저장소 `modules/<이름>/`)은 완성된 규칙이 아니라 원칙과 작성 항목만 갖고 있고, 이 스킬이 프로젝트를 읽어 그 프로젝트 전용 규칙을 쓴다.

이 스킬은 하네스를 처음 보는 사용자가 따라오는 안내 절차다. 사용자가 이 하네스의 기능·스킬·설정 이름을 모른다고 가정한다. 「대화 방식」을 모든 단계에 적용한다. 사용자 문장에는 「기능」이라고 쓰고 「모듈」·`modules/`는 쓰지 않는다.

시작 전에 `~/.agents/docs/harness-guide.md`를 Read한다(정본 위치, 기능 설치 규약 §4, 설정값·비밀값 §2.1).

## 입력

| 항목 | 값 |
|---|---|
| 프로젝트 루트 | 현재 작업 폴더. 다르면 사용자에게 확인 |
| 하네스 저장소 | 전역 `~/.agents/harness.toml`의 `[harness] repo_dir` (설치 스크립트가 기록). 아래에서 `<repo>` |
| 기능 목록 | `<repo>/README.md` 「기능 목록」 표(소제목: 전역 또는 프로젝트 / 프로젝트 전용 / 레거시 모듈), `<repo>/modules/*/MODULE.md`(맨 위 「범위:」「구성:」 줄) |
| 프로젝트 전용(기본) | `<repo>/modules/guards/`(보안 훅), `<repo>/modules/verify/`(정적 검사), `<repo>/modules/reviewbot/`(검토 에이전트) — 표에 기본으로 켠 행 |
| 공통 부품 | `<repo>/core/hook_io.py`, `<repo>/core/gen_hook_configs.py` |
| 설정 예시 | 프로젝트 `<repo>/modules/guards/harness.example.toml`, 전역 `<repo>/core/harness.example.toml`, 각 MODULE.md 「설정 키」 |
| 결과 기준 | 루트 `AGENTS.md` 구성은 [references/agents-md-template.md](references/agents-md-template.md) |

`[harness] repo_dir`가 없으면 멈추고 설치 스크립트(`python <repo>/install/install.py global --tools ...`)를 먼저 돌리라고 안내한다. 설치 전체 순서는 저장소 루트 `start.md`(이 스킬 폴더에서 두 단계 위)를 따른다.

## 실행 모드

| 모드 | 판단 | 차이 |
|---|---|---|
| 처음 | `.agents/harness.toml`이 없음 | 아래 단계를 모두 진행 |
| 다시 맞춤 | `.agents/harness.toml`이 있음 | 단계마다 지금 값과 새 값의 차이만 보여 주고 바꿀 것만 고친다. 사용자가 손으로 고친 규칙 문장은 덮어쓰지 않는다 |
| 기능 켜기·끄기 | 사용자가 기능 이름을 지정 | 1·2단계는 건너뛰고 3단계부터 그 기능만 |

다시 맞춤·기능 켜기 끄기에서는 훅이 이미 등록돼 있다. 훅 스크립트, `.agents/hooks/hooks.toml`, `harness.toml`의 `[guard]` 절은 고칠 파일 목록을 먼저 보여 주고 사용자가 보호 해제 승인 키워드(`[guard] hook_approval`, 기본 `gohook`)를 단독 입력한 턴에만 고친다. 사용자에게는 "보호된 훅 파일이라 채팅에 `<단어>` 한 단어만 입력해 주셔야 이번 한 번 고칠 수 있습니다"처럼 설명한다.

## 대화 방식

### 시작 안내 (첫 응답, 조사 전에)

1. 하네스가 무엇인지 두 줄: 에이전트가 이 프로젝트에서 지킬 규칙, 위험한 동작을 막는 훅, 자주 하는 작업을 묶은 스킬·서브에이전트, DB·로그 연결(MCP)을 프로젝트에 맞게 만든다
2. 진행 순서: 1 프로젝트 파악 → 2 형상관리 → 3 쓸 기능 고르기 → 4 기능별 세부 설정 → 5 설치 → 6 점검. 단계마다 무엇을 묻는지 한 줄
3. 확인 전에는 파일을 쓰지 않고, 모르는 질문은 "모름"이나 "나중에"로 답해도 된다는 것

### 무엇을 묻나

MODULE.md 「사용자 안내」의 질문마다 아래 표시가 붙어 있다. 표시대로만 묻는다.

| 표시 | 언제 묻나 | 해당하는 것 |
|---|---|---|
| `[항상]` | 설치 때 반드시 | 보안·안전: DB 환경 목록·운영 구분·쓰기 규칙, 에이전트 커밋·푸시 권한, 보호 해제 승인 키워드(2단계), 운영 서버(FTP 등) 접속 사용 |
| `[못 찾을 때]` | 코드·설정·VCS 기록에서 확실히 찾지 못한 경우만 | 규칙이 달라지는 값(언어·프레임워크 버전), 작성자 이름(VCS 사용자 이름과 최근 커밋 작성자가 모두 비었을 때. 찾았으면 묻지도 「이렇게 정했습니다」에 쓰지도 않음), 감지되지 않는 기능을 쓸지 |
| `[처음 쓸 때]` | 설치 때 묻지 않음. 그 기능을 처음 쓸 때 그 스킬이 묻고 `harness.toml`에 적음 | 외부 도구·폴더 경로(빌드 도구, 리포트 원본, 로그 폴더, 로그 서버 목록), 기능 세부 설정 |
| `[묻지 않음]` | 묻지 않고 추천값으로 정함 | 그 밖의 모든 것 |

- `[처음 쓸 때]` 값은 비워 두고 최종 보고 「나중에 필요한 것」에 기능별로 한 줄씩 적는다
- 「사용자 안내」에 표시가 없는 질문은 `[묻지 않음]`으로 본다

### 줄이기 (처음 세팅하는 사용자가 지치지 않게)

- 「무엇을 묻나」의 `[항상]`·`[못 찾을 때]`만 묻는다. 나머지는 추천값으로 정하거나 처음 쓸 때로 미룬다
- 코드에서 읽은 값, 추천값으로 정한 값은 단계 끝에 「이렇게 정했습니다」 짧은 목록으로만 보여 준다. 바꾸고 싶으면 말하라고 한 줄 덧붙인다
- 근거(`파일:줄`), 감지 과정, 판정 이유는 사용자에게 보여 주지 않는다. `.agents/tmp/YYYYMMDD_setup_detect.md`에만 적는다. 사용자가 "왜"라고 물을 때만 답한다
- 사용자가 볼 필요가 없는 값은 「이렇게 정했습니다」에도 쓰지 않는다: 시험 데이터 접두, 비워 둔 값, 해당 없는 설정, 내부 판단 메모
- `harness.toml` 키 이름(`[paths] local_log_dir` 등)과 TOML 원문을 사용자 문장에 쓰지 않는다. 그 값이 무엇에 쓰이는지로 말한다(예: 로컬 로그 폴더)
- 한 단계의 질문은 많아야 5개. 넘으면 중요한 것만 묻고 나머지는 추천값으로 정한다
- 초안은 전문이 아니라 결과 요약(무엇을 켜고 어디에 무엇이 생기는지)으로 보여 준다

### 질문 형식

- 단계 머리는 `## 1단계 · 프로젝트 파악`처럼 쓴다(`1/6` 형식 금지)
- 「이렇게 정했습니다」는 `| 항목 | 값 |` 표로 보여 준다
- 질문 도구가 없을 때(아래 「질문 도구」) 질문은 코드 블록에 넣지 않는다. 마크다운으로 아래 모양으로 쓴다. 보기는 번호를 붙여 사용자가 질문마다 숫자만 답하면 되게 한다

  ```markdown
  ## Q1. IntelliJ 검색 (jetbrains)
  ### 이 프로젝트 작업 중에 IntelliJ를 켜 두나요?
  1. 예 (추천)
  2. 아니오
  ```

  - `##` 줄: 질문 번호와 기능 이름(사용자 말, 하네스 이름은 괄호)
  - `###` 줄: 실제 질문. 보조 설명이 필요하면 그 아래 한두 줄
  - 그 질문에만 해당하는 설명(예: 보호 해제 승인 키워드가 무엇인지)은 그 질문 안에 쓴다. 단계 전체 머리에 몰아 쓰지 않는다
  - 보기에는 "쓰지 않음"(기능을 아예 끄는 것)을 빠뜨리지 않는다. 직접 입력이 필요한 보기는 "직접 입력"으로 두고 무엇을 적으면 되는지 한 줄
- MODULE.md 「사용자 안내」에 표나 설명 문단(예: DB 환경별 현재 동작 표, DB 승인 키워드 설명)이 있으면 그 질문 바로 위에 반드시 보여 준다. 「줄이기」 대상이 아니다. 표의 환경 이름·DB 승인 키워드는 프로젝트에서 찾은 값으로 바꿔 채운다
- "모름"은 질문마다 쓰지 않고, 단계 첫머리에 한 번 "모르면 '모름'이라고 답하시면 추천값으로 둡니다"
- 질문 문구의 재료는 기능의 MODULE.md 「사용자 안내」다. 그 절의 정하는 것·추천·모름 항목은 판단용이고, 사용자에게는 위 모양으로 줄여 보여 준다
- 답은 `1 1 2`처럼 질문 순서대로 숫자만 적어도 된다고 단계 끝에 한 번 알린다
- 사용자가 숫자 대신 말로 답하면(예: "도구없음-끔") 말을 우선한다. 보기와 맞지 않거나 뜻이 둘로 읽히면 짐작해서 진행하지 않고 그 질문만 다시 묻는다

### 질문 도구 (있으면 반드시 쓴다)

선택 화면으로 묻는 도구가 있으면 위 마크다운 질문 대신 그 도구로 묻는다. 찾지 못하거나 호출이 실패하면 마크다운 질문으로 묻는다.

| 도구 | 이름 | 제한 |
|---|---|---|
| Claude Code | `AskUserQuestion` | 한 번에 질문 1~4개, 질문마다 보기 2~4개. "Other"(직접 입력)가 자동으로 붙음. 추천 보기는 맨 앞에 두고 이름 끝에 "(Recommended)" |
| Cursor | `AskQuestion` | 질문마다 보기 목록, 여러 개 고르기 옵션. 직접 입력 칸이 없으므로 직접 입력이 필요한 질문은 "직접 입력" 보기를 두고, 고르면 채팅으로 이어서 받음. 모델·모드에 따라 도구가 없을 수 있음 |
| 그 밖 | — | 마크다운 질문 |

- 질문 화면이 떠 있는 동안 같은 응답의 채팅 글은 사용자에게 안 보일 수 있다. 그래서
  - 도구 질문의 질문 문구는 그것만 읽고 답할 수 있게 쓴다. "위 표", "아래 요약"처럼 화면 밖 내용을 가리키지 않는다
  - 표·요약을 봐야 답할 수 있는 질문(DB 환경별 동작 표, 설치 초안 확인)은 도구를 쓰지 않는다. 표·요약과 마크다운 질문을 채팅으로 보여 주고 답을 기다린다
  - 한 질문을 도구와 마크다운으로 두 번 묻지 않는다. 둘 중 하나만
  - 「이렇게 정했습니다」 표는 도구 질문이 없는 응답(앞 단계 답을 반영한 직후의 응답)에 보여 준다
- 질문 제목에는 기능 이름(사용자 말)을, 보기 설명에는 그 보기를 고르면 생기는 결과를 한 줄로 쓴다
- 한 단계 질문이 도구 한도(Claude Code 4개)를 넘으면 두 번에 나눠 묻는다
- 사용자가 답을 건너뛰거나 취소하면 추천값으로 정하지 않고, 그 질문을 채팅으로 다시 묻는다

### 용어

- 도구 일반 용어(훅, MCP, 스킬, 서브에이전트, AGENTS.md)는 그대로 쓴다
- 이 하네스에서 만든 이름은 사용자 문장에 단독으로 쓰지 않는다. 하는 일을 먼저 말하고 이름은 괄호로 붙인다

  | 하네스 이름 | 사용자에게 |
  |---|---|
  | 기능 id(comment-gen, jetbrains, log-debug …) | 기능 설명 (예: 변경 이력 주석 자동 달기 (comment-gen)) |
  | 스킬·서브에이전트 이름(verify, sqlbot …) | 하는 일 (예: 변경 검증 스킬 (verify)) |
  | 승인어(go, gotest …) | DB 승인 키워드: INSERT·UPDATE 같은 SQL 전에 채팅에 입력하는 키워드. "허락 단어"라고 쓰지 않는다 |
  | `gohook` | 보호 해제 승인 키워드 |
  | 비밀 파일, 비밀 폴더 | "계정·비밀번호 파일", "계정·비밀번호를 두는 폴더". 에이전트도 못 보게 프로젝트 밖에 둔다는 설명을 붙임 |
  | `harness.toml` 키 이름 | 그 값이 쓰이는 곳 (예: 이력 주석에 찍힐 이름) |
  | fixture, venv, MCP Reload | 하는 일과 사용자가 누를 메뉴·입력할 명령 |

## 공통 규칙

- 단계마다 초안을 채팅에 보여 주고 사용자 확인을 받은 뒤에 파일을 쓴다
- 유지보수 프로젝트의 모든 사실은 파일을 열어 확인하고 근거(`파일:줄`)를 감지 기록 파일에 적는다(사용자에게는 보여 주지 않음, 「줄이기」). 폴더·파일 이름만 보고 추론하지 않는다. 설정 파일 하나만 보고 전체를 단정하지 않는다(예: 매퍼 DTD는 매퍼 XML 여러 개에서 확인). 확인하지 못한 항목은 `미확인`으로 두고 질문 목록에 올린다
- VCS에서 제외된 설정 파일(`.gitignore` 등에 있어 사본에 없는 빌드·서버 설정)이 판단에 필요하면 사용자에게 내용이나 위치를 묻는다
- 근거는 이 프로젝트 루트 안의 파일과 사용자 답변만 쓴다. 같은 머신의 다른 프로젝트(이름이 같거나 비슷한 폴더 포함)의 `AGENTS.md`·`.agents/`·`harness.toml`은 열지 않는다. 사용자가 특정 프로젝트의 하네스를 옮기라고 지시한 경우만 예외
- 프로젝트 밖 경로는 도구 위치(JDK, 생성기, 앱 서버, 로그 폴더) 확인에만 쓰고, 프로젝트 설정에 적힌 경로나 사용자가 알려 준 경로를 `Test-Path`·`ls`로 확인하는 데서 그친다. 드라이브 전체를 재귀 검색하지 않는다. 경로를 모르면 묻는다
- 신규 프로젝트는 코드에서 감지할 것이 없으므로 같은 항목을 질문으로 정한다. 일반 지식으로 채우지 않는다
- 버전별 사실(문법 제약, 지원 기능)은 프로젝트 코드나 공식 문서로 확인한 것만 쓴다
- 값(사람·조직·경로·서버·ID)은 규칙 본문에 쓰지 않고 `harness.toml` 키로 둔다. 문서에는 `{섹션.키}`로 적는다
- 계정·비밀번호·토큰 값은 묻지도 받지도 않는다. 5단계에서 키만 적힌 빈 파일을 만들고 사용자가 값을 채운다
- 설정 파일(TOML·JSON·`.env`)은 편집 도구로 UTF-8(BOM 없음)로 쓴다. 셸의 `Set-Content`·`Out-File`로 쓰지 않는다
- 큰 파일은 전문을 Read하지 않는다. 검색으로 줄을 잡고 구간만 읽는다
- 이 스킬이 쓰는 일회성 파일(감지 결과, 초안)은 `.agents/tmp/YYYYMMDD_setup_*`

## 1. 프로젝트 파악

1. 유지보수인지 신규인지 정한다. 소스 파일이 있으면 유지보수로 정하고 묻지 않는다
2. 기존 지시 파일을 읽는다: 루트·폴더 `AGENTS.md`, `CLAUDE.md`, `.cursor/rules/`, `.github/copilot-instructions.md`, `README`. 있는 규칙은 버리지 않고 새 구성의 어느 절로 갈지 파일별 한 줄 표로 보여 준다
   - 옮길 때는 규칙 단위로 모두 옮긴다(공식·순서·형식·예외 포함). 요약해서 줄이지 않는다. 전역 지시와 같은 내용만 뺀다
   - 다른 도구는 `.cursor/rules/*.mdc`를 읽지 않으므로(Claude Code·Codex), 옮긴 뒤 원본은 그대로 두되 보고에 "내용은 AGENTS.md·docs로 옮겼고, 지우면 Cursor에서도 같은 규칙을 씀"을 적는다
   - 5단계에서 원본 규칙마다 옮긴 위치를 감지 기록 파일에 적고, 빠진 규칙이 없는지 6단계에서 확인한다
3. 스택을 확정한다

   | 대상 | 근거 (유지보수) |
   |---|---|
   | 언어·버전 | 빌드 파일(`pom.xml`, `build.gradle`, `package.json`, `pyproject.toml`), IDE 설정(`.classpath`, `.idea/misc.xml`, `.settings/`), 실제 문법 |
   | 프레임워크·버전 | 의존성, `WEB-INF/lib`의 jar 이름, 설정 XML |
   | 매퍼·ORM | 의존성, 매퍼 XML의 DTD |
   | DB | JDBC 드라이버, 데이터소스 설정 |
   | UI·리포트 | 화면 원본 확장자, 프로젝트 파일, 뷰어 경로 |
   | 로거 | 기본 패키지(업무 코드) 전체에서 로거 호출 수를 세어 가장 많은 것. 프레임워크 패키지 표본으로 정하지 않는다 |
   | 형상관리 이중 사용 | 커밋 메시지·폴더에 다른 VCS 흔적(예: SVN 반영 커밋)이 있으면 팀 저장소와 개인 저장소를 구분해 적는다 |
   | 앱 서버·빌드 도구 | 서버 설정, 빌드 스크립트 유무 |

4. 폴더 지도를 만든다: 소스 루트, 계층(화면 → 컨트롤러 → 서비스 → DAO → 매퍼 등)과 각 폴더, 빌드 산출물(고치면 안 되는 곳)
5. 폴더별 `AGENTS.md`를 둘 폴더를 정한다(묻지 않음). 기준: 그 폴더 파일을 고칠 때만 필요한 규칙이 있는 곳(harness-guide §3)
6. DB 테이블 구조를 확인할 근거를 정한다(테이블 정의서, DDL, ERD, 마이그레이션). 찾으면 묻지 않는다. 못 찾았을 때만 묻는다(`[못 찾을 때]`): 경로 알려 줌 / DB 직접 조회 / 없음
7. 테스트 정책(묻지 않음): 테스트 소스(`src/test`, `*_test.*`, `tests/`)나 기존 규칙에 테스트 실행 지시가 있으면 그 방식(테스트 명령, 실행 시점)을 규칙에 쓴다. "테스트 파일을 만들지 않음"은 테스트 체계가 전혀 없을 때만 쓴다
8. 확인을 받은 뒤 루트 `AGENTS.md` 초안을 템플릿 구성대로 쓴다(파일 쓰기는 5단계에서 한 번에)

## 2. 형상관리

1. 감지: `.git`·`.svn`, 원격 주소(`git remote -v`, `svn info`), 현재 브랜치와 브랜치 목록
2. 브랜치 흐름: 브랜치 이름과 병합 기록에서 읽어 「이렇게 정했습니다」에 적는다(묻지 않음)
3. 커밋 메시지 규칙: 최근 50개 메시지(`git log -n 50 --format=%s`, `svn log -l 50`)에서 접두·언어·티켓 번호 형식을 뽑아 「이렇게 정했습니다」에 적는다(묻지 않음)
4. `[항상]` 묻는 것은 셋: 에이전트 커밋(사용자 요청 시만 (추천) / 허용 / 금지), 푸시(금지 (추천) / 허용), 보호 해제 승인 키워드
   - 보호 해제 승인 키워드 질문에만 이 설명을 붙인다(단계 머리에 쓰지 않음): "훅과 보안 설정 파일은 에이전트가 고치지 못하게 잠겨 있습니다. 고쳐야 할 때는 에이전트가 고칠 파일 목록을 먼저 보여 주고, 사용자가 채팅에 이 키워드 하나만 입력하면 그 한 번만 풀립니다. 다음 메시지를 보내면 다시 잠깁니다."
   - 보기: `gohook` 그대로 (추천) / 직접 입력. DB 승인 키워드와 겹치지 않게 한다
   - 결과는 `[guard] hook_approval`
5. 하네스 파일(`.agents/`)을 저장소에 넣을지: 이미 VCS 제외 설정이 있으면 그대로 두고 묻지 않는다. 없을 때만 "넣으면 팀원도 같은 규칙을 쓰고, 빼면 내 PC에만 있다"로 묻는다
   - 넣지 않음: `.gitignore`(또는 `svn:ignore`)에 `.agents/`
   - 넣음: 적어도 `.agents/tmp/`, `.agents/hooks/state/`, `.agents/mcp-servers/singleton/state/`는 제외. `harness.toml`에 내부 서버 주소가 들어가면 그 파일도 제외할지 묻는다
6. 결과는 루트 `AGENTS.md`의 형상관리 절로 간다. 커밋 메시지 형식처럼 여러 스킬이 쓰는 값은 프로젝트 문서나 `harness.toml`로

## 3. 쓸 기능 고르기

기능마다 따로 묻지 않는다. AskUserQuestion·AskQuestion 같은 질문 도구도 이 단계에서는 쓰지 않는다(표를 봐야 답할 수 있는 질문이다).

1. `<repo>/modules/*/MODULE.md`를 모두 읽고 「감지 신호」를 프로젝트에서 찾는다(Glob·Grep, 근거 `파일:줄`은 감지 기록 파일에만)
   - 같은 역할의 변형(예: iBatis 2 / MyBatis 3)은 하나만 고른다
2. 채팅에 번호 매긴 표를 보여 준다. `<repo>/README.md` 「기능 목록」 표(이름 | 하는 일 | 구성) 맨 앞에 `#` 열만 붙인 같은 표이고, 범위 소제목(전역 또는 프로젝트 / 프로젝트 전용 / 레거시 모듈)도 README와 같다. 번호는 표 전체에 이어 붙인다
   - 전역 또는 프로젝트: README 그 절의 기능을 모두 넣는다. 이미 전역에 깔려 있으면 하는 일 칸 끝에 `(전역 설치됨)`. 권장 위치는 전역
   - 프로젝트 전용: README 그 절의 기능을 모두 넣는다. guards·verify·reviewbot은 기본으로 켠 행. 이슈·이력 주석·로그는 감지 신호가 약해도 넣는다
   - 레거시 모듈: 감지된 기능만 표에 넣는다. 감지 안 된 레거시 모듈은 표 아래 한 줄로 이름만 적는다
3. 표 아래에서 확인만 받는다
   - 표의 기능을 전부 쓸지
   - 「전역 또는 프로젝트」를 추천(전역)대로 깔지
   - 빼거나 위치를 바꿀 것은 번호와 말로 받는다(예: `5 프로젝트`, `9 빼`). 기능마다 되묻지 않는다
   - 기능 안의 변형(예: 이슈 도구 Jira / GitHub Issues / 없음)은 MODULE.md 「사용자 안내」의 해당 질문을 표 아래 같은 응답에 함께 묻는다
4. 답을 반영한 표를 다시 보여 주고 "설치함(어디에·어떤 방식) / 설치 안 함"을 기능마다 한 줄로 되짚는다. "도구 없음(설치함)"과 "쓰지 않음(설치 안 함)"처럼 헷갈리는 답은 되짚은 줄로 확인받는다
5. 고른 결과를 기록한다(5단계): 프로젝트 기능은 `.agents/harness.toml` `[harness] modules`, 전역 기능은 `~/.agents/harness.toml` `[harness] modules`

## 4. 기능별 세부 설정 (규칙 작성)

켠 기능마다 MODULE.md를 다시 Read하고 다음을 한다.

1. 「원칙」은 그대로 결과 문서에 옮긴다. 프로젝트와 맞지 않는 원칙이 있으면 지우지 말고 사용자에게 묻는다
2. 「규칙 작성 항목」 표의 각 항목을 「읽을 곳」에서 찾아 채운다. 근거 `파일:줄`은 감지 기록 파일에. 못 찾으면 추천값이 있는 항목은 추천값으로 두고, 없으면 `미확인`으로 두고 질문 후보에 넣는다(「줄이기」의 5개 제한)
   - 표의 항목은 하나도 빼지 않는다. 결과 문서에 항목마다 채운 줄이나 `미확인` 줄이 있어야 한다(6단계에서 확인)
3. 기능 폴더에 `rules.md`가 있으면 그것을 바탕으로 하고, 「프로젝트에서 채울 항목」을 프로젝트 사실로 채운다
4. 질문은 「사용자 안내」의 「물어볼 것」을 쓴다. 여러 기능의 질문을 한 번에 묶되 기능별 소제목(기능 설명)을 단다
5. 결과는 MODULE.md의 「결과 →」 위치(폴더 `AGENTS.md`, `.agents/docs/<문서>.md`)에 쓴다. 새 폴더 `AGENTS.md`와 `.agents/docs/` 문서는 루트 `AGENTS.md`의 지도·조건부 문서 표에 한 줄씩 추가한다
6. 「설정 키」를 모아 `harness.toml` 초안에 넣는다. 값은 프로젝트 설정에서 읽고, 경로는 지금 값을 기본값으로 보여 주고 확인만 받는다
7. 기능 문서가 프로젝트 문서를 요구하면(예: issue-flow의 `project-doc-template.md`, mapper의 verify fixture 표) 그 템플릿대로 쓴다
8. 기능 문서가 다른 기능과의 조합 규칙을 적어 두었으면 반영한다(예: Nexacro를 켜면 이력 주석 금지 구간 추가)

기능 사이에 같은 사실이 나오면(예: Java 버전, DB 방언) 한 문서에만 쓰고 다른 곳은 위치를 가리킨다.

## 5. 설치

순서가 중요하다. 훅을 등록하는 7번 전까지는 가드가 꺼져 있다.

`<.agents>`는 그 기능을 설치할 위치다. 전역이면 `~/.agents`, 프로젝트면 `<프로젝트>/.agents`.

```text
전역으로 고른 기능
├─ 파일 → ~/.agents/ (아래 표)
├─ hooks.toml 조각 → ~/.agents/hooks/hooks.toml 끝에 이어 붙임 (없으면 새로 만듦)
└─ python ~/.agents/hooks/gen_hook_configs.py --scope global --tools <쓰는 도구>

프로젝트로 고른 기능 + guards + verify + reviewbot
├─ 파일 → <프로젝트>/.agents/
├─ hooks.toml → .agents/hooks/hooks.toml (guards가 뼈대, 다른 기능 훅은 이어 붙임)
└─ python .agents/hooks/gen_hook_configs.py --scope project --tools <쓰는 도구>
```

1. 프로젝트 전용으로 켠 guards·verify·reviewbot(기본으로 켠 경우 포함)
   - guards: `modules/guards/hooks/*.py`·`hooks/tests/` → `.agents/hooks/`, `modules/guards/hooks.toml` → `.agents/hooks/hooks.toml`, `<repo>/core/hook_io.py`·`<repo>/core/gen_hook_configs.py` → `.agents/hooks/`에 링크
   - verify: `modules/verify/skills/verify/` → `.agents/skills/verify/`, `modules/verify/scripts/restore_eol.py` → `.agents/scripts/`
   - reviewbot: `modules/reviewbot/agents/reviewbot.md` → `.agents/agents/`
2. 켠 기능(전역 또는 프로젝트 · 나머지 프로젝트 전용 · 레거시 모듈)의 파일을 harness-guide §4 규약대로 고른 위치에 복사한다

   | 기능 폴더 안 | 설치 위치 |
   |---|---|
   | `skills/`, `agents/` | `<.agents>/skills/`, `<.agents>/agents/` |
   | `hooks/*.py`, `hooks/tests/` | `<.agents>/hooks/`, `<.agents>/hooks/tests/` |
   | `hooks.toml` | `<.agents>/hooks/hooks.toml` 끝에 이어 붙임 |
   | `harness.fragment.toml` | `<.agents>/harness.toml`에 합침. `[guard] shell_block_patterns` 같은 목록은 기존 목록에 더함 |
   | `verify.md` | `.agents/skills/verify/checks/<기능>.md` (프로젝트만) |
   | `scripts/`, `mcp-servers/` | `<.agents>/scripts/`, `<.agents>/mcp-servers/` |
   | agent-rules `AGENTS.md` | 전역: `~/.agents/AGENTS.md`로 링크. 프로젝트: 루트 `AGENTS.md` 앞부분에 옮김 |
   | `MODULE.md`, `rules.md`, `project-doc-template.md` | 복사하지 않음 (4단계 결과 문서의 재료) |

   - 전역에 깔 기능 중 훅이 있는 것: `~/.agents/hooks/hook_io.py`가 있는지 확인한다(전역 기반 설치 `install.py global`이 링크). 없으면 `install.py global`을 먼저 다시 돌린다
   - 복사 전에 기능마다 「설치할 것 / 빼는 것」과 설치 위치를 감지 기록 파일에 먼저 적고, 이 단계의 나머지(훅 목록, `harness.toml`, MCP, 계정 파일)도 모두 그 목록을 따른다
     - 기능 변형에 따라 설치 파일이 다르면(MODULE.md 「설치 변형」) 고른 변형의 파일만 넣고, 변형에서 빼라는 절·줄·키를 지우고 자리표시를 채운다
     - 사용자가 끈 기능은 넣지 않는다. 기능 안의 일부(예: 로그 분석은 켜고 원격 FTP는 끔)를 끈 경우 MODULE.md가 그 부분이라고 적은 파일·훅 목록 줄·MCP 항목·계정 파일·설정 절을 모두 뺀다. 보고에 "나중에 켜려면 set-up-harness로 그 기능만 다시 켬"을 적는다
   - 전역 위치(`~/.agents`, `~/.claude`, `~/.cursor`, `~/.codex`)에 파일이나 등록을 더하는 기능은 설치 전에 무엇을 어디에 더하는지 초안에 적고 확인받는다
   - 여러 파일 복사는 셸로 한다. 다시 맞춤에서 셸 가드가 경로를 막으면(예: DB MCP 서버 폴더) 명령을 보여 주고 사용자가 직접 실행하게 한다
3. 같은 훅 스크립트가 전역(`~/.agents/hooks/hooks.toml`, `~/.claude/settings.json`, `~/.cursor/hooks.json`의 스크립트 이름)에 이미 있으면 프로젝트 `hooks.toml`에 넣지 않고 그 사실을 보고에 적는다
4. `.agents/harness.toml`을 쓴다: `<repo>/modules/guards/harness.example.toml`의 절 + 켠 기능의 설정 키 + 조각. 맨 위 `name`은 계정 파일 폴더 이름(`<secrets_dir>/<name>/`)이 된다. 전역으로 깐 기능의 설정 키는 `~/.agents/harness.toml`에 쓴다
   - 조각(`harness.fragment.toml`)의 패턴 줄은 글자 그대로 옮긴다. 작은따옴표 문자열(`'...'`)을 큰따옴표로 바꾸거나 `\`를 더하거나 빼지 않는다
   - 쓴 직후 검사: `harness.toml`이 `tomllib`로 읽히는지, `[guard] shell_block_patterns`의 모든 패턴이 Python `re.compile`로 컴파일되는지, 조각에 `# sample:`로 적힌 명령에 각 패턴이 실제로 걸리는지(역슬래시를 두 번 쓰면 컴파일은 되지만 아무것도 막지 못한다). 실패하면 7번(훅 등록) 전에 고친다. 훅이 켜진 뒤에는 `[guard]`를 고치려면 보호 해제 승인 키워드가 필요하다
5. 1·4단계의 루트 `AGENTS.md`, 폴더 `AGENTS.md`, `.agents/docs/` 문서를 쓴다. 기존 `CLAUDE.md`가 있으면 내용을 `AGENTS.md`로 옮기고 지울지 묻는다(남기면 Claude Code가 `AGENTS.md`를 읽지 않는다. 남겨야 하면 첫 줄 `@AGENTS.md`)
6. MCP와 계정 파일
   - 켠 기능의 `mcp-servers/<이름>/README.md` 「MCP 등록」대로 `.agents/mcp.json`을 쓴다. 환경별 실행 파일이 필요한 기능(예: tibero `launch_<env>.py`)은 README의 내용으로 환경마다 만든다
   - 로컬 Python MCP 서버(DB·FTP)는 공유 서버(url) 방식으로 등록한다
     - **db-mcp**: 설정 스캔→확인으로 `[guard.db]`를 채운다. MCP 이름 `db-<env>`. 어댑터(tibero 등)가 없으면 hooks만 두고 runnable DB·mcp.json `db-*`·ports `db-*`는 만들지 않는다
     - `singleton/` 폴더는 한 기능에서만 복사한다. 우선순위 db-mcp > log-debug(원격 로그만). MODULE.md 「포함 파일」과 같게
     - `ports.example.json`을 바탕으로 `.agents/mcp-servers/singleton/ports.json`을 만든다. DB는 `db-<env>`+어댑터 script, FTP는 script만(`kind` 없음). 포트 18761부터, `python`은 venv 절대경로
     - `.agents/mcp.json`에는 같은 이름·포트의 `url` 항목을, `.agents/mcp.stdio.json`에는 README의 stdio 항목을 쓴다(되돌림용)
     - 의존성 설치 뒤 `python .agents/mcp-servers/singleton/daemon.py start`를 실행한다. 계정 파일이 비어 있으면 그 서버는 기동에 실패한다(`started-port-not-ready`, `state/<이름>.log`). 계정을 채운 뒤 다시 `start`
     - 로그온 자동 시작(시작프로그램 바로가기)은 만들지 않는다. 7단계 보고 「사용자 할 일」에 singleton README 「로그온 자동 시작」을 안내한다
   - 켠 기능의 `*.env.example`마다 `<secrets_dir>/<name>/<이름>.env`를 만든다. 내용은 키만 있고 값은 비운다. 파일이 이미 있으면 건드리지 않는다. 다시 맞춤에서 훅이 이 폴더를 막으면 경로와 키 목록을 보여 주고 사용자가 만든다
   - MCP 서버가 쓰는 Python 패키지를 `[tools] python`으로 설치한다(`-m pip install -r <requirements.txt>`). 설치 전에 무엇을 설치하는지 알리고 확인받는다
7. 훅 등록. `[tools] python`이 비어 있으면 Python 경로를 찾아 보여 주고 확인받아 전역 `harness.toml`에 쓴다. 이 시점부터 가드가 켜진다
   - 프로젝트: `python .agents/hooks/gen_hook_configs.py --scope project --tools <쓰는 도구>`
   - 전역 훅이 있는 기능을 전역에 깔았으면: `python ~/.agents/hooks/gen_hook_configs.py --scope global --tools <쓰는 도구>`. 전역 등록 파일에서 `~/.agents/hooks/` 항목만 바꾸고 사용자가 따로 등록한 훅은 남긴다. Codex 전역 등록은 만들지 않는다
8. 도구 연결(링크·Codex 에이전트 TOML·MCP 설정)
   - 프로젝트: `python <repo>/install/install.py project <프로젝트 루트> --tools <쓰는 도구>`
   - 전역에 기능을 깔았으면: `python <repo>/install/install.py global --tools <쓰는 도구>`를 다시 실행(전역 지시 import·전역 스킬 링크)

## 7. 보고

1. 첫 줄: 켠 기능과 결과 한 줄
2. 만든·고친 파일 트리
3. 나중에 필요한 것: `[처음 쓸 때]` 항목을 기능별 한 줄로(그 기능을 처음 쓰면 에이전트가 물어본다는 것), 아직 모르는 것은 무엇이 안 되는지
4. 사용자가 할 일(번호 목록). 항목마다 왜 하는지 → 어디서 → 무엇을. 예:
   - DB 계정 넣기: 에이전트가 DB를 조회하려면 계정이 필요하다 → `<파일 경로>`를 메모장으로 열기 → `=` 뒤에 계정·비밀번호를 적고 저장
   - DB·로그 연결 다시 읽기: 새로 만든 연결을 도구가 읽게 한다 → Cursor는 Settings → MCP에서 새로고침, Claude Code는 채팅에 `/mcp`
   - DB·로그 서버 켜기: 재부팅하면 공유 서버가 꺼져 연결이 실패한다 → 터미널에서 `python .agents/mcp-servers/singleton/daemon.py start`. 매번 하기 싫으면 `.agents/mcp-servers/singleton/README.md` 「로그온 자동 시작」대로 시작프로그램 바로가기를 만든다
   - Codex를 쓰면 채팅에 `/hooks`를 입력해 새 훅을 허용
   - Cursor를 쓰고 전역 지시를 처음 깔았으면 `~/.agents/AGENTS.md` 내용을 Settings → Rules → User Rules에 붙여 넣기
