# 티켓 확인 (issue-flow)

티켓으로 작업을 시작해 계획·구현·검증까지 잇는다. 배포 등 후속 단계는 프로젝트 스킬이 맡는다.

값 표기 `{…}`·`[tracker.fields] …`는 `.agents/harness.toml`의 같은 키를 Read해서 쓴다.

회사·프로젝트마다 다른 값(내 담당 조회 조건, 필드 옵션 ID, 상태 이름과 전환, 착수 시 기입할 필드, 검증 후 넘길 단계)은 프로젝트 issue-flow 문서(`.agents/docs/issue-flow.md`, set-up-harness가 작성)에 있다. 이 스킬 문서에 적지 않는다.

## 트리거

| 항목 | 값 |
|------|-----|
| 키워드 | `issue-flow`, `ticket`, `지라`, `지라 확인`, `티켓 확인`, `티켓 목록`, `내 티켓`, `작업 시작` |
| 티켓 키 (Jira·GitHub) | `<KEY>-{n}` (실제 접두는 스킬 설명과 프로젝트 issue-flow 문서) |
| 도구 | 프로젝트 issue-flow 문서 §도구: Jira(Atlassian MCP) / GitHub Issues(GitHub MCP) / 없음(요청 붙여넣기) |

- (Jira·GitHub) 채팅에 티켓 키 또는 순수숫자가 이미 있으면 목록 단계를 건너뛰고 착수 필드 단계부터
- (도구 없음) 트리거 직후 요청 붙여넣기를 안내하고, 붙여넣으면 계획 단계부터

## 도구별 표식

제목 끝, 표 행의 첫 칸 끝, 목록 항목 맨 앞에 붙은 괄호 속 도구 이름(Jira, GitHub, 도구 없음)은 그 도구에서만 쓰는 부분이라는 표식이다. 둘을 가운뎃점으로 이은 표식은 이슈 관리 도구가 있을 때(Jira·GitHub Issues)다. 표식이 없으면 항상 쓴다. 설치 때 쓰지 않는 도구의 부분은 지워져 있다(기능 MODULE.md 「설치 변형」).

## 턴 분리 — 선택 UI 금지

AskQuestion(Cursor)·AskUserQuestion(Claude Code) 같은 선택 카드를 쓰지 않는다. 카드가 채팅 본문의 조회 요약을 가린다. 선택은 다음 채팅 메시지로만 받는다.

| 턴 | 출력 | 금지 |
|----|------|------|
| 트리거 직후 (Jira) | 내 담당 조회 → `aggregate_assigned.py` 집계 → §1~§2 출력 → 턴 종료 | 보고 후 추가 도구, 셸 `python -c` 집계 |
| 트리거 직후 (GitHub) | 내 담당 조회 → MCP 응답을 §1~§2 표로 옮김 → 턴 종료 | 보고 후 추가 도구, 셸 `python -c` 집계 |
| 트리거 직후 (도구 없음) | 요청 붙여넣기 안내([references/tracker.md](references/tracker.md) 「요청 붙여넣기」) → 턴 종료 | 요청 내용 추측 |
| 다음 메시지 키 / 숫자 (Jira·GitHub) | §4(물을 칸만). 물을 칸 0이면 §5만 | — |
| 칸 토큰 (Jira·GitHub) | 기입 → 첨부 → 전환 → §실행결과 → 계획 단계([계획 산출](references/workflow.md#계획-산출)) | 계획 없이 구현 |
| 「진행」 (Jira·GitHub) | 물을 칸 0일 때만. 기입 없이 첨부·전환. 남은 칸이 있으면 그 칸만 재안내 | — |
| 붙여넣은 요청 (도구 없음) | 계획 단계([계획 산출](references/workflow.md#계획-산출)) | 계획 없이 구현 |
| 계획 단계 | 대상 화면·코드 확정 → §착수분석 → 파이프 A. 확정 못 하면 §대상미확정만 | 소스 패치 |

2. 실행: [references/workflow.md](references/workflow.md)
3. 계획 파일 쓰기 전: [references/plan-format.md](references/plan-format.md)
4. 보고 직전: [references/response-format.md](references/response-format.md) 해당 §
5. 엣지·사례: [references/examples.md](references/examples.md) (필요 시)

프로젝트 issue-flow 문서가 없으면 조회 조건·옵션 ID·상태 이름을 추측하지 않는다. 문서가 없다고 보고하고 set-up-harness 실행 또는 값 입력을 요청한다.

## 처음 쓸 때 확인 (Jira·GitHub)

설치 때 묻지 않고 비워 둔 값은 그 기능을 처음 쓸 때 한 번 묻고 적는다. `.agents/harness.toml`은 편집 도구로 고친다(UTF-8, BOM 없음. 절이 없으면 파일 끝에 추가). `[guard]` 절은 건드리지 않는다. issue-flow 문서의 `미정`은 아직 묻지 않은 값, `없음`은 쓰지 않기로 정한 값이다(`없음`은 다시 묻지 않는다).

### 착수 필드·상태 전환 (Jira·GitHub)

키·숫자를 받아 §4로 가기 전, issue-flow 문서 §착수 필드 또는 §상태 전환이 `미정`이면

1. 한 문장으로 설명한다: "작업을 시작할 때 티켓에 자동으로 적을 칸과 바꿀 상태가 아직 정해지지 않아, 목록에서 골라 주셔야 합니다. 아무것도 적지 않기로 해도 됩니다"
2. 이 티켓으로 필드 목록과 전환 목록을 조회만 해서 번호 목록으로 보여 주고 턴을 끝낸다
   - (Jira) 필드 `getJiraIssueTypeMetaWithFields`, 전환 `getTransitionsForJiraIssue`
   - (GitHub) 라벨·마일스톤, open/closed
3. 고른 칸의 ID는 `[tracker.fields]`에, 이름·묻는 순서·타입은 issue-flow 문서 §착수 필드에, select 옵션은 §필드 옵션에, 전환은 §상태 전환에 적는다. 「아무것도 적지 않음」이면 그 절을 `없음`으로 적는다
4. 이어서 §4로 간다. 이 단계에서는 티켓에 아무것도 쓰지 않는다(승인 게이트 그대로)

### 첨부 토큰 파일 (Jira)

첨부 다운로드 전, `[paths] jira_token_file`이 비어 있고 티켓에 첨부가 있으면

1. 한 문장으로 설명한다: "티켓 첨부 파일을 에이전트가 직접 받으려면 Atlassian API 토큰을 적어 둘 파일이 필요한데 아직 정해지지 않아, 내려받기를 쓸지와 그 파일 위치를 정해 주셔야 합니다"
2. 선택지: 내려받기(추천 위치 `<secrets_dir>/<프로젝트 이름>/jira_token.txt`. 에이전트가 열 수 없는 비밀 폴더) / 직접 받아 경로를 알려 줌
3. 내려받기면 위치를 `[paths] jira_token_file`에 적고, 사용자가 그 파일에 1행 이메일, 2행 토큰을 직접 적게 안내한다(발급 URL은 [references/tracker.md](references/tracker.md) 「첨부 다운로드」). 에이전트는 토큰 파일을 열지 않는다. 사용자가 다 적었다고 하면 받고, 아니면 이번 첨부는 보류로 보고한다
4. 직접 받음이면 값을 비워 두고, 이번 대화에서는 다시 묻지 않는다

## 승인 게이트

- (Jira·GitHub) 승인 없이 금지: 이슈 필드 기입, 상태 전환, 댓글 작성
  - (Jira) `editJiraIssue`·`transitionJiraIssue`
  - (GitHub) `issue_write`
- (Jira·GitHub) 목록·착수 필드 안내 단계는 조회와 채팅 보고만 한다
- (Jira·GitHub) 기입 대상은 프로젝트 issue-flow 문서 §착수 필드에 적힌 필드뿐이다. 요청 본문·다른 필드는 쓰지 않는다
- (Jira·GitHub) 티켓 키·필드 ID·옵션 ID·transition ID를 지어내지 않는다. 필드 ID는 `[tracker.fields]`, 옵션 ID는 프로젝트 issue-flow 문서, transition은 조회 결과의 이름 매칭으로만 얻는다
- 후속 단계(배포 등)는 사용자 승인 전에 시작하지 않는다

## reviewbot SKIP / 호출 (파이프 A·B 공통)

프로젝트에 `reviewbot` 에이전트가 없으면 이 절 전체를 SKIP으로 본다.

부모가 호출 전에 판정한다. `reviewbot`은 SKIP을 다시 판단하지 않는다. 판정 축은 작업 종류 이름이 아니라 분기 복잡도·수정 범위다.

SKIP (전부 충족):

- 화면 1개(+ 필요 시 쿼리·맵퍼 1개) 수준, 파급 없음
- 분기가 얕음: 기존 한 경로에 조건·필드만 붙이거나, 옵션으로 기존 동작을 켜고 끄기만 함
- 예: 조회 조건·그리드 컬럼·라벨·문구·표시 형식 변경

반드시 호출 (하나라도 해당):

- 여러 함수·콜백·분기에 같은 항목이 흩어져 빠지기 쉬움
- 저장·콜백·유효성 검사 분기 신설이 넓음
- 쿼리·DAO·공통 함수·세션 파라미터 패턴 변경, 수정 화면 2개 이상, `파급` 있음

SKIP 시 채팅·계획 `## 리뷰`에 `[review] SKIP · 간단변경 ({사유 한 줄})` 한 줄만. 파이프 B에서 SKIP이면 오류·누락 0건으로 보고 후속 제안 게이트를 통과시킨다(`/verify` FAIL=0은 필수).

## 서브에이전트 호출 한도

분석·리뷰 서브에이전트 공통. 토큰은 파일 크기보다 Fresh 중복과 범위 없는 지시에서 샌다.

A. 종류당 Fresh 1회 + resume

- 단계(착수분석·파이프 A·파이프 B)마다 Fresh 호출은 종류당 최대 1회
- 부모는 반환된 agent ID를 보관한다. 같은 단계의 2회째부터는 resume만 쓴다. 보낼 것은 질문 또는 미확인 항목 목록뿐이다

| 하네스 | resume |
|--------|--------|
| Cursor | Task `resume` 인자에 agent ID |
| Claude Code | 반환된 agent ID로 `SendMessage` |

- Fresh 2회째 예외: agent ID 유실·세션 변경 / mode 변경(plan→diff) / 질문이 이전 범위와 무관(사유 한 줄)
- 금지: "조금 더 깊게"로 같은 에이전트를 새로 띄움

B. 선례 조사

- 범위는 이번 작업에 대응하는 화면·파일만. 호출 관계 전체로 넓히지 않는다
- 기본은 부모가 검색(IDE MCP 또는 Grep, 결과 수 제한) → 맞은 구간만 Read → 선례 요약(파일:줄)을 에이전트 입력에 붙인다
- 부모 검색으로 안 풀리면 좁은 호출 1회: 질문 1~3개 + 대상 파일 지정. 검색 0건이면 사용자에게 선례 화면을 묻는다

C. reviewbot 재호출

- 파이프 A mode=plan 1회, 파이프 B mode=diff 1회(SKIP이면 0회). 반영 후 재리뷰 없음
- 사용자가 "다시 봐줘"를 명시하면 resume(A)로 허용

D. 입력 3칸 (Fresh·resume 공통). 원칙·출력 형식·언어는 전역 `AGENTS.md` 「에이전트 간 호출 프로토콜」

| 칸 | 내용 | 에이전트가 할 일 |
|----|------|-------------|
| 확인됨 | 부모·이전 에이전트가 확인한 사실 + 파일:줄 | 재확인 안 함. 핵심 1~2개만 표본 확인 |
| 미확인 | 부모가 확인 못 한 항목 | 확인 |
| 인접 탐색 | 다른 호출처·분기, 같은 파라미터·쿼리를 쓰는 다른 화면 | 여기서 구멍을 찾음 |

## 파이프 A — 계획 파일 → reviewbot → 후처리

§착수분석 후 [계획 산출](references/workflow.md#계획-산출)로 계획 파일을 다 쓴 직후 이어서 수행한다(사용자 지시 없어도).

1. SKIP 기준이면 호출 생략 → `## 리뷰`에 SKIP 한 줄
2. 호출 시 `reviewbot` mode=plan. 넘길 것: 계획 파일 경로, 분석 요약, 티켓 요구사항(본문·첨부 요약), `범위:` 한 줄(함수·쿼리 id), 같은 성격 항목의 등장 위치 목록
3. 지적을 계획에 반영하고 `## 리뷰`에 지적별 반영 결과(반영 / 미반영 + 사유)를 적는다. 선례와 같은 동작을 결함으로 짚은 지적은 `미반영(선례 동작과 동일)`으로 적어 사용자에게 넘긴다. 0건이면 `[review] mode=plan · 지적 0건` 한 줄
4. comment-gen 기능을 켰으면 comment-gen 스킬로 변경 이력 주석 계획을 반영한다(소스 수정 없음)

## 파이프 B — todo → 빌드 → `/verify` → reviewbot → 후속 제안

1. 계획 todo가 있으면 전부 completed. 프로젝트 issue-flow 문서 §검증 후 단계에 빌드·생성 단계가 있고 대상 파일이 바뀌었으면 먼저 실행
2. `/verify`(정적 검사) 실행
   - FAIL=0이면 SKIP 기준 판정. 호출이면 `reviewbot` mode=diff. 넘길 것: 계획 파일 경로(없으면 `없음`), 변경 파일 목록과 `git diff HEAD`, `[verify]` 결과, `범위:` 한 줄
   - 오류·누락 1건 이상 → 후속 제안 금지 → 지적 기준으로 수정 계획
   - 과잉·파급만 있으면 채팅에 보여주고 사용자가 고친다/둔다를 고른다. 고쳤으면 `/verify`부터 다시
3. 실행 검증이 필요하면(화면·API 동작 변경) test 스킬로 넘긴다. 프로젝트에 test 스킬이 없으면 확인 시나리오를 채팅에 적고 사용자 확인을 받는다
4. FAIL=0이고 (reviewbot SKIP 또는 오류·누락 0건)일 때만 후속 제안. 내용은 프로젝트 issue-flow 문서 §검증 후 단계. 문서에 없으면 제안하지 않고 완료 보고만 한다. 티켓당 제안 1회
5. FAIL>0 → 후속 제안 금지 → 계획 단계로 돌아가 FAIL ID·대상 파일 기준으로 원인 분석·수정 계획. 소스 패치는 계획 승인 후
6. `/verify`는 규칙 기반 PASS/FAIL, `reviewbot`은 판단형 지적(오류·누락·파급·과잉)이다. `reviewbot`은 `/verify` 항목을 다시 검사하지 않는다

## 역할 분담

| 역할 | 담당 | 하지 않음 |
