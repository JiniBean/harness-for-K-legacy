# log-debug

값 표기 `{…}`는 `.agents/harness.toml`의 같은 키를 Read해서 쓴다. 로그 서버·파일 규칙·회사 확인 방법처럼 프로젝트마다 다른 내용은 프로젝트의 `.agents/docs/`(set-up-harness가 만든 로그 문서)에 있다.

## 모드 고르기

| 신호 | 모드 |
|---|---|
| `운영 로그`, 운영·고객사 문의, 운영 서버명, FTP | 운영 |
| `로컬 로그`, 최신·개발 서버 로그 | 로컬 |
| 위 신호가 없음 | 어느 로그인지 먼저 묻는다 |

두 모드 모두 목적이 두 가지다. 둘 다 로그에서 끝나지 않고 화면·맵퍼·컨트롤러까지 확인한다. 업무 소스는 읽기만 한다.

1. 타임라인: 특정 건의 INSERT/UPDATE 시각, 수행 사용자, URI. 화면·맵퍼로 왜 갱신됐는지 판단
2. 기능 오류: 저장 실패 등의 예외. 같은 URI의 화면·맵퍼에서 원인

질의에 업무 키(건 번호·컬럼, "누가 바꿨나")가 있으면 타임라인, 오류 메시지면 기능 오류, 둘 다면 타임라인 먼저.

## 처음 쓸 때 확인

모드를 고른 직후, 그 모드에 필요한 `harness.toml` 값이 비어 있으면 먼저 채운다. 값은 `.agents/harness.toml`에 편집 도구로 적는다(UTF-8, BOM 없음. 절이 없으면 파일 끝에 추가). `[guard]`·`[guard.ftp]` 절은 직접 고치지 않는다. 경로를 찾을 때는 프로젝트 안이나 사용자가 말한 폴더만 본다. 드라이브 전체를 뒤지지 않는다.

운영 모드: `[[ftp.servers]]`가 없거나 사용자가 말한 서버가 목록에 없을 때

1. FTP 연결이 설치돼 있지 않으면(`.agents/mcp-servers/ftp/server.py`가 없거나 FTP MCP가 연결되지 않음. 같은 폴더의 `log_digest.py`는 원격 로그를 끈 설치에도 있으므로 폴더 유무로 판단하지 않는다) 여기서 멈추고 "운영 로그 기능이 꺼져 있어 set-up-harness로 log-debug 기능의 원격 로그를 다시 켜야 합니다"라고 안내한다
2. 한 문장으로 설명한다: "운영 로그를 받으려면 로그 서버 주소와 로그가 쌓이는 폴더를 알아야 하는데 아직 등록된 서버가 없어, 서버 정보를 알려 주셔야 합니다"
3. 서버마다 묻는다: 호스트·포트(생략하면 `[ftp] port_default`), 채팅에서 부를 짧은 영문 이름(`alias`, 영문 소문자·숫자, 지역·용도 약자 추천), 지역·용도 메모, 오늘 로그 폴더, 지난 로그 폴더. 폴더를 모르면 비워 둔다
4. 서버마다 `[[ftp.servers]]` 블록(`alias`, `host`, `port`, `region`, `log_cwd_current`, `log_cwd_backup`, `log_name_hint`)을 추가한다. FTP MCP는 호출마다 이 설정을 다시 읽으므로 MCP를 다시 켜지 않아도 된다
5. 셸 직접 접속 차단: 새 호스트가 `[guard] ftp_hosts`에 없으면 고치지 않고 "셸에서 이 서버로 직접 접속하는 명령을 막는 목록은 보호된 훅 설정이라, 채팅에 `gohook` 한 단어만 입력해 주셔야 고칠 수 있습니다"라고 안내하고, 바꿀 줄을 그대로 보여 준다
   ```toml
   ftp_hosts = ["<기존 호스트>", "<새 호스트>"]
   ```
   `gohook` 턴에 이 한 줄만 고친다. 적용 전에는 다운로드(B)로 가지 않는다. 사용자가 적용하지 않겠다고 하면 셸 차단이 빠진다는 것을 한 줄로 알리고 진행한다
6. 계정: 비밀 파일 `<secrets_dir>/<프로젝트 이름>/ftp.env`에 `FTP_USER_<ALIAS>`·`FTP_PASSWORD_<ALIAS>`(ALIAS는 대문자, 모든 서버가 같으면 공통 `FTP_USER`·`FTP_PASSWORD`)를 사용자가 메모장으로 직접 적게 안내한다. 에이전트는 이 파일을 열지 않는다
7. 폴더를 비워 둔 서버는 계정이 들어간 뒤 `ftp_list`로 루트를 조회해 보여 주고, 사용자가 고른 폴더를 `log_cwd_current`·`log_cwd_backup`에 적는다. 목록에 보이는 파일 이름 형식을 `log_name_hint`에 적는다
8. 서버 조회 순서가 정해지면 프로젝트 로그 문서에 한 줄 더한다. 이어서 「A. 질의 확정」을 진행한다

로컬 모드: `[paths] local_log_dir`가 비어 있을 때

1. 프로젝트의 로그 설정(`log4j*.xml`, `log4j*.properties`, `logback*.xml`)에서 파일 출력 경로를 찾는다. 하나로 확실하면 그 값을 적고 한 줄로 알린다
2. 못 찾으면 한 문장으로 설명한다: "내 PC의 WAS 로그를 보려면 로그 파일이 쌓이는 폴더를 알아야 하는데 설정에서 찾지 못해, 폴더 경로를 알려 주시거나 찾아볼 폴더를 지정해 주셔야 합니다"
3. 사용자가 경로를 주면 그 값을, 찾아볼 폴더를 주면 그 아래에서 찾은 로그 폴더를 보여 주고 확인받은 값을 `[paths] local_log_dir`에 적는다. 이어서 「로컬 모드」를 진행한다

## 운영 모드

질의 확정(A)을 끝내기 전에는 로그를 받거나 검색하지 않는다.

### A. 질의 확정

1. 회사·스키마: 회사명 또는 회사 ID로 DB를 SELECT해 스키마·회사 ID를 확정한다(조회 테이블은 프로젝트 로그 문서). 여러 행이면 사용자가 고른다
2. 검색 대상: 사용자 용어를 로그 검색 키로 바꾼다. DB 스키마 기준 문서(테이블 정의서)로 테이블·컬럼을 확인하고, 건이 DB에 없으면 그렇게 보고한다. 컬럼 후보가 여럿이면 사용자가 고른다
3. 구간·파일: 서버 목록은 `harness.toml` `[[ftp.servers]]`(파일 이름 규칙은 `log_name_hint`), 서버 조회 순서는 프로젝트 로그 문서

   | 사용자 입력 | 동작 |
   |---|---|
   | 날짜·시간·어제/오늘 | 그 구간 (애매하면 ±1일 버퍼 제안) |
   | 구간 없음 | 해당 건의 등록·수정 일시로 제안. 타임라인은 전후 24시간 |
   | DB에도 단서 없음 | 구간을 묻는다. 전체 일괄 다운로드 금지 |
   | 기능 오류 + 시각 없음 | 오늘 또는 live 파일만 제안 |

   `ftp_get`은 미리보기. 본 분석은 텍스트 로그면 `ftp_slice`로 구간만, zip/gz면 `ftp_download`
4. 확인 블록을 보여 주고, 사용자가 맞다고 할 때만 B로 간다

```text
[로그 질의 확정]
목적: 타임라인 | 기능오류
회사: {회사명} → 스키마={} / 회사 ID={}
업무키: {사용자 키} → {DB 키} (DB 조회)
변경 항목: {사용자 표현} → {TABLE}.{COLUMN}
구간: {YYYY-MM-DD HH:mm ~ HH:mm} (출처: 사용자 지정 | DB 수정 일시)
다운로드: 서버 순서와 대상 파일 → 로컬 .agents/tmp/ftp/...
확인 후 다운로드·분석을 진행합니다. 수정·추가할 항목이 있으면 알려주세요.
```

### B. 분석 (확인 후)

A는 부모가 하고, B는 서브에이전트 `logbot`이 한다(확정 파일만 slice/download, 요약, 요청 원문). `logbot`은 화면·맵퍼·원인을 `미확인` + URI로만 돌려준다. URI나 `Dao.method`가 있으면 부모가 `sqlbot`(맵퍼)·`nexabot`(화면, 해당 기능을 켰을 때)을 부른 뒤에만 "왜"를 적는다.

1. 확정 파일만 받는다. zip/gz는 풀지 않는다(요약기가 직접 읽음). 원격·로컬 원본 수정 금지
2. 요약: `log_digest.py --group {스키마} --corp {회사 ID} [--from ..] [--to ..] [--key {업무 키}] FILE...` — 대상 회사 요청만 1줄씩
3. 원문: 요약에서 고른 요청만 `log_digest.py --puuid {PUUID} FILE...`. 로그 원문을 Grep·Read로 직접 읽지 않는다
4. 아래 답변 형식으로만 답한다

## 로컬 모드

1. 로그 위치: 워크스페이스의 `{paths.local_log_dir}/`. 원격 다운로드 금지
2. 파일 고르기
   - 오늘 파일 먼저(파일명 일자 또는 수정 시각). 여러 개면 지금 시각과 가까운 것, 동률이면 live 우선. 그다음 시각 내림차순
   - 답변 앞에 경로 / 수정 시각 / 크기를 적는다
   - 크기 0만 보고 비었다고 단정하지 않는다. 끝 N줄이나 Grep로 내용을 확인한 뒤 판단하고, 진짜 빈 파일은 건너뛰며 한 줄로 적는다
   - 통째로 읽지 않고 끝에서 거슬러 올라가며 문의 구간을 찾는다
3. DB 고르기: 로그의 회사 ID가 `{test.dev_corp}`이면 개발 DB, `{test.test_corp}`이면 테스트 DB. 그 밖이면 로그의 스키마가 있는 DB를 SELECT로 찾아 하나로 확정한다
4. 파일을 고른 뒤 Grep·타임라인은 `logbot`, 맵퍼는 `sqlbot`, 화면은 `nexabot`
5. DB는 SELECT만(결과 행 수 제한). 쓰기는 프로젝트 DB 승인 절차를 따른다

## 답변 형식

없으면 `해당없음` / `미확인`. 로그에 없는 DML을 있다고 하지 않는다. "왜"는 화면·맵퍼를 본 뒤에만 적는다.

```text
[로그]
모드: 운영 | 로컬     목적: 타임라인 | 기능오류
대상: 스키마= / 회사 ID= / 회사명=
키: 업무키= / TABLE.COLUMN=
구간: YYYY-MM-DD HH:mm
파일: 원격 → 로컬 (또는 로컬 경로 / 수정 시각 / 크기)
```

타임라인 (INSERT/UPDATE/DELETE만 시간순):

```text
시각 | 사용자 | URI | SQL종류 | 테이블 | 비고
화면: 화면 파일 / 이벤트 / 서비스 URL
맵퍼: 매퍼 파일 statement id
원인: 사용자 저장 | 다른 API | 맵퍼/화면 오류 가능 | 미확인
근거: 시각 있는 원문 2~5줄
```

기능 오류:

```text
요청: URI / 사용자 / IP / 요청 ID
예외: 시각, 클래스, 메시지 (같은 예외 횟수)
화면: 화면 파일 / 이벤트
맵퍼: 매퍼 파일 statement id
원인: (소스와 로그가 맞을 때만)
근거: 예외·SQL 원문 2~5줄
```

"누가"는 그 DML과 같은 요청(요청 ID·스레드)의 로그인 사용자다.
